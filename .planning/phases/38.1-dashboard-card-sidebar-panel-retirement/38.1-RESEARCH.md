## HA frontend/Lovelace findings
1. `homeassistant.components.frontend.add_extra_js_url(hass, url, es5=False)` / `remove_extra_js_url(hass, url, es5=False)` (frontend/__init__.py ~417-431) keep a `UrlManager` in `hass.data[DATA_EXTRA_MODULE_URL]`; the list is pushed to every frontend session (`websocket_subscribe_extra_js`, index render ~883). Dedupe/removal is by exact URL string. This is the supported integration-owned way to load a card module; it covers the card picker and storage and YAML dashboards, and needs no Lovelace resource.
2. Lovelace (`components/lovelace/__init__.py`): `resource_mode` is `storage` or `yaml` (lines ~121-185). In storage mode resources are user/UI-managed (HA logs "define resources via user interface"); in YAML mode they come from `lovelace: resources:`. An integration cannot and should not write either -> auto-creating a resource is both unsupported and a duplicate-resource risk. Chosen design avoids it.
3. `panel_custom.async_register_panel` is runtime-only (not persisted), so panel retirement needs no storage migration; unloading/restarting removes the sidebar entry. Current code uses it with `frontend.async_remove_panel` on release.
4. Custom card contract (HA docs): element needs `setConfig(config)` (throw on invalid), `set hass`, optional `getCardSize()`, `getGridOptions()` (sections view), static `getStubConfig()`; picker discovery via `window.customCards.push({type, name, description, preview, documentationURL})` where `type` is the element name without `custom:`.
5. `static_paths` cannot be unregistered; existing code handles by deleting the served bundle (404) and `route_registered` flag - keep.
