# Playlist Playback Architecture Research

**Milestone:** v1.0 Playlist Playback & Management  
**Researched:** 2026-10-10  
**Confidence:** MEDIUM

## Existing Boundaries

| Component | Current responsibility | Playlist implication |
|-----------|------------------------|----------------------|
| Native HA integration | Caches speakers, resolves HA media-source IDs, submits authenticated commands | Natural owner of HA provider browsing and source resolution; no browse method or queue features currently exist. |
| Ingress React app | Calls the add-on's REST API and WebSocket | No HA media-source or HA-auth connection was found, so custom playlist authoring needs a secure HA-side catalog interface. |
| FastAPI bridge | Validates native commands and invokes the player | Accepts one `play_media` URL command; no playlist model or queue API exists. |
| Playback bridge | Runs FFmpeg and the audio player per speaker | `_watch_processes` currently clears state and returns to idle when one source ends; it is the natural completion hook for sequential advancement. |

## Candidate Data Flow

```text
Ingress user
  -> authenticated HA-side media catalog interface
  -> select HA media IDs and persist ordered playlist metadata on the HA side
  -> HA integration resolves the next ID at playback time
  -> authenticated add-on bridge starts one validated URL
  -> process completion advances the queue unless stopped, replaced, or failed
  -> playback state/event updates return to HA and ingress
```

The catalog interface between ingress and HA is unresolved. Do not place a Home Assistant bearer token in the add-on or expose it to browser storage. A supported HA WebSocket integration command or another HA-owned authenticated surface should be evaluated during planning.

## Ownership Recommendations

- Persist playlist names, ordered media-source identifiers, and any minimal display metadata with Home Assistant-owned storage; resolve source IDs immediately before playback.
- Keep the actual FFmpeg process lifecycle and automatic advancement in the bridge, which owns the per-speaker processes.
- Use a queue generation/ownership token so stop, replacement, speaker disconnect, and older process-completion callbacks cannot advance stale playlists.
- Report the current item and bounded failure state through existing bridge events/state, rather than inferring playlist position in the frontend.
