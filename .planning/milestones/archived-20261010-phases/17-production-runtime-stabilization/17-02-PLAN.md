<feature>
  <name>Deterministic reconnect and BlueZ recovery under runtime failure</name>
  <files>modules/bridge/backend/bl_haos/bluetooth/reconnect.py, modules/bridge/backend/bl_haos/bluetooth/manager.py, modules/bridge/tests/test_auto_reconnect.py, modules/bridge/tests/test_bluetooth_manager.py, modules/bridge/tests/test_health.py, modules/bridge/tests/test_bridge_sil.py</files>
  <behavior>
    - Duplicate ticks and duplicate device events for one normalized address create one active reconnect task and leave no orphan ownership after completion, cancellation, unregister, or engine stop.
    - A failed reconnect publishes disconnected/reconnecting observations with bounded attempt metadata; a successful retry publishes connected and resets retry counters; no contradictory connected state is emitted after a failed/cancelled attempt.
    - A stale BlueZ method/object failure invalidates the cached object, performs one bounded refresh, and classifies an unrecoverable result as stale_bluez_object rather than silently treating it as an ordinary missing device.
    - D-Bus transport loss is distinguishable from an absent speaker object, triggers a bounded bus/object recovery path, and publishes dbus_disconnected or dbus_unavailable without falsely reporting Bluetooth healthy.
    - Reconnect exhaustion publishes unavailable with reconnect_exhausted, preserves the last safe failure, and waits for breaker cooldown/explicit recovery before scheduling another attempt.
    - Health snapshots and versioned WebSocket/API observations retain normalized addresses, transition reasons, failure classifications, bounded detail, and compatible existing fields.
  </behavior>
  <implementation>Use existing asyncio, dbus-fast, Pydantic, BluetoothManager, AutoReconnectEngine, and HealthRegistry seams. Preserve the current public API and normalized-address ownership. Make recovery injectable for SIL tests; bound refresh/reinitialization attempts; distinguish transport loss, stale object, sink/dependency unavailability, and exhaustion; and ensure task cleanup is handled in success, exception, cancellation, unregister, and shutdown paths. Do not add dependencies or redesign Phase 18 input validation.</implementation>
</feature>
